# 用已收割的客机产物重判 #201 和 #250

两名执行者并行接入保存和负零件的文件判据。复核用了 10 份历史客机收据，其中 4 份有完整产物，6 份来自失败运行。此次只在宿主读取文件，没有派发客机任务或变更飞书状态。

| --- | --- | ---: | ---: |
| [#201 保存并独立重开](evidence/feishu-140-201-202-2026-11-25/row-201-hyperv/README.md) | 保存件的变换与 12 个三角面沿 X 移动 10 mm，重开输入与保存件字节相同。未移动、反向移动均被拒绝。实际启动第二个进程和画面读回见原客机记录。 | 137.137、137.356 秒 | 0.079、0.083 秒 |
| [#250 添加负零件](evidence/feishu-250-251-2026-11-25/row-250-hyperv/README.md) | 唯一对象包含主体和负件，目标区域挤出路径从 535.317 mm 降到 0，对侧仍有挤出，两侧工况均为 68 层。用基线替换负件 G-code 会被拒绝。菜单和画布颜色见原客机记录。 | 156.495、157.447 秒 | 0.122、0.123 秒 |

离线耗时是每份收据分别启动五次独立 Python 进程，计入启动、读取、核验和 JSON 输出后取中位数。使用同一台 Windows 宿主，文件可能已在系统缓存中。历史 GUI 时间从派发到该轮场景日志关闭。人工工时和首次编写判据的净耗时未测。

## 哪些失败可以少跑一轮

- #201 的四份历史 RED 中，三份在准备或编辑阶段停止。第四份 `054dd881` 已保存新位置，离线可确认位移和文件哈希。重开输入缺失，工具保留已通过的保存检查，整体复核返回失败。修复方向可以直接收窄到编辑进程退出和独立重开。
- #250 的两份历史 RED 分别缺少负件项目和成对的 G-code。首次失败的日志记录在子菜单处中止，第二次已经完成负件切片，导出未生成 G-code。这两份需要重新执行相应的 GUI 操作取得产物。
- 另在临时目录将 #250 的负件 G-code 换成基线文件。原清单检测出文件不符，连清单一并更新后，实际几何判据仍拒绝。原归档保持原样。

因此这次能计量的是产物就绪后一次判据迭代的耗时。六份历史失败中有一份支持部分重判，其余五份缺少关键输入。没有实测省掉的客机轮数或新用例领取至交付的时间差。

## 复现

从仓库根目录运行，可同时传入多份收据。输出中 `historical_summary` 是原客机日志的摘要，`result.checks` 是本次逐项结论。任一收据的文件缺失、证据不符或反例未被拒绝，命令返回非零。

```powershell
python tools/replay_case_evidence.py docs/runs/evidence/feishu-140-201-202-2026-11-25/row-201-hyperv/1216dc9e-run1-receipt.json
python tools/replay_case_evidence.py docs/runs/evidence/feishu-250-251-2026-11-25/row-250-hyperv/a7a65272-run1-receipt.json
```

工具校对收据中的日志 SHA-256、同轮工件清单中的大小和 SHA-256，以及日志里的保存文件摘要或几何读数。历史收据没有为工件清单本身记录哈希。#250 使用原 GUI 的几何判据和默认立方体夹具。

## 下一条的计时口径

适合试用的是飞书 #249「添加部件」。它可以复用 #250 的右键子菜单和文件选择步骤。保存的 3MF 可以验证新增部件归属于对象 A；「选中 A 时连同新部件一起选中」需要客机界面证据。按领取、判据与反例就绪、入队、客机启动、取回首份可重判产物、首次可信结论记录时间；每次失败注明是界面动作、缺产物、判据错误还是产品行为差异。两名执行者并行的墙钟和人工工时分别记账。
