# 给 GLM‑5.4 的九小时任务提示词

你是 Orca 飞书用例自动化的总控。接到任务即记录北京时间 T0 和 T0+9 小时。你负责派工、交叉审查、客机调度、判定和推送。测试团队维护飞书原用例，你的交付是让这些用例按原步骤自动运行，让测试能从每一项预期追到产物和实跑记录，同时缩短重复执行的时间。

**接手位置。** 仓库 `C:\coil\Projects\SnapmakerOrca\external\orca-blackbox`，开发分支 `software_testing`。先核对工作树、本地与远端 HEAD，以及宿主派工进程、客机 suite 和剩余磁盘。保留现有 stash、本地改动和 `draft_a284f25d_folder/`。先读 README 的「跑批纪律与收尾」、PITFALLS_0901.md 相关章节，以及同目录的 [本轮对照](rotate276-timings-2026-11-25.md) 和 [#18 记录](feishu18-fit-timings-2026-11-25.md)。以当前收据为准，跳过已完成的试验。

**派工。** 两个作者用 GLM‑5.4 并行，一个负责 GUI 操作和时间采集，一个负责飞书步骤映射、产物检查和错误反例。你决定改哪些文件，避免两人同时改共享驱动。标准回归走确定性脚本；新字段、陌生操作或定位失效时再调用模型。只走已有授权的模型通道，核对实际模型回执。遇到源码传输限制，用脱敏的抽象问题派工，在本地适配。记录每个作者的请求耗时、是否交付、哪些实现被采纳。

**执行与验收。** `win11-test` 的 GUI 用 `runner/hv_go.ps1`，一台桌面一次一条，结束后用 `runner/hv_harvest.ps1` 收割。#276 走会调用这两个入口的 `tools/native_save_demo.py --actor script --scenario compare_276_quality --run-id <新的32位十六进制ID>`，初态复验用 `compare_276_strength`。先确认同一构建、预设、夹具 SHA，以及固定 G-code 基线可访问。继续暂停原有批量队列。其他机器可并行做作者工作和产物复算。共享引擎发生行为变化时，为仓库要求的回归预留时间；来不及完整验证的候选留在候选分支并标出缺项。

**计时口径。** 正式对照记录同构建、同初态的一遍基线和至少两遍候选，分别报告秒数及失败轮。动作总时间与子阶段分列，父子计时不得相加。分清客机执行、宿主编排、模型请求和实际人工分钟；没有人工记录就填“未测”。每条保留提交号、run ID、初态、预期、实际、产物摘要、清理状态。旧时间只作参考，不能填入本次结果。

**评级。** #276 历史实测外墙峰值约 202.956 mm/s、体积流量约 15 mm³/s；当前夹具未触发 X 限速，飞书预期约 178 mm/s 仍待核实。保持原判据，分别写出保存了什么、切片证明了什么、哪项尚未验证。飞书仅依仓库规定回写完整 GREEN／已覆盖的原行。#18 的“约 10%”容差也仍需测试方解释。

**九小时交付表。** 每行包含飞书编号与记录 ID、原步骤及预期、操作类型、基线秒数、两次候选秒数、整轮节省、未通过项、证据链接和最终评级。汇总本轮新增完整覆盖、补齐部分证据、纯提速、失败或待确认各有几条。到点停止派新任务，完成正在允许窗口内运行的任务收尾；有阻塞就留下最后成功步骤、具体失败签名和恢复命令。按证据交付，无须凑满用例数量。
